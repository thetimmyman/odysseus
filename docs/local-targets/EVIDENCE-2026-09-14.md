## Why this document is a measurement record, not a design note

PS-579 established that a green result against a fixture we authored ourselves
proves internal consistency, not capability. The same trap applies here: a
target registry that *declares* three nodes is worthless if the declarations are
wrong. So every field below was read off a live node, and the fleet snapshot in
`FLEET-SNAPSHOT.json` is generated by the shipped `probe_fleet()` — not written
by hand.

## Findings that change how the fleet must be routed

1. **The declared capability list is not authoritative — in either direction.**
   `local-rtx4500` advertises no `tools` capability and yet returned a correct
   native tool call. A registry that trusted `capabilities` would have written
   off the fastest node in the fleet for all agent work. `native_tools` is
   therefore set only from a proven call; the declared list is recorded as a
   hint. (Same failure mode as PS-579's reviewer authority: a self-description
   is not evidence.)

2. **The declared context length is not the serving window — and the two nodes
   serve wildly different windows.** Both declare 262144. The RTX node serves
   **32768** and the MS-R1 serves **4096** (both read from `/api/ps` for the
   resident model; the live snapshot in `FLEET-SNAPSHOT.json` carries both).
   A packet sized from the declared number would be dispatched into a window
   that does not exist — and one sized for the RTX window would silently
   overflow on the MS-R1. `served_context` is recorded separately and
   `safe_working_context` stays `None` until measured, never inferred from the
   declared maximum.

3. **"Same model tag" hides a ~13× throughput difference and a different memory
   path.** `qwen3.8:27b` on the RTX node decodes at 37.1 tok/s from VRAM; the
   same tag on the MS-R1 decodes at 2.83 tok/s from system RAM. Both are
   healthy. Treating them as one `local_qwen` pool would make a queue depth of
   "2 idle nodes" say nothing about usable capacity.

4. **The two nodes run different runtimes** (0.32.11 vs 0.33.3) and report
   different quantization metadata (`unknown` vs `Q4_K_M`). Capability probes
   must tolerate a runtime that predates a request key — the probe retries the
   tool question without `think` so a version difference cannot masquerade as a
   capability difference.

5. **Capability-complete records are not fitness-complete records, and the
   default tie-break is a trap.** The registry probe deliberately does not time
   anything (a cold 27B load on the ARM node costs minutes, and a probe that
   expensive gets switched off). With no timings recorded, the first LIVE
   selection run picked `local-msr1` for BOTH requirements — by the
   deterministic `target_id` tie-break, i.e. the **13× slower** node, purely
   because "local-msr1" sorts before "local-rtx4500". Feeding the measured
   decode rates back in through `timings_by_target` flips both selections to
   `local-rtx4500`:

   ```
   # fitness-blind (no timings in the live record)
   select(['native_tools'])    -> local-msr1   (host=msr1)
   # fitness-driven (measured decode rates applied)
   select(['native_tools'])    -> local-rtx4500 (host=minipc)
   select(['readonly_analysis']) -> local-rtx4500 (host=minipc)
   ```

   Consequence for PS-605: routing must supply measured fitness (or pin a
   target explicitly). A deterministic order is not the same thing as a
   *fitness*-informed one, and shipping the former while calling it load-aware
   would be exactly the kind of quiet mislabeling this stack keeps catching.

## Not done here / next slices

  a context-growth experiment before any number is defensible.
- Semantic canary, streaming/cancellation proof and max-safe-concurrency are
  named in the PS-632 contract but not yet measured. They are ABSENT from the
  record rather than filled with a guess.
- Selection is a deterministic fitness order over measured records. Wiring it
  into the router is PS-605's owned surface; the `execution_catalog.py`
  integration seam (`bulk_local`) belongs to the unmerged
  `work/ps-623-execution-catalog` branch and was not touched here.
- The scratch harnesses (`~/scratch/ps632/probe.py`, `decode_rate.py`,
  `fleet_snapshot.py`) are evidence tooling, not shipped code.
- PS-579's conclusion is UNCHANGED by this work: nothing here creates an
  auto-approve class or any reviewer authority. These measurements classify
  targets for *dispatch*, not models for *acceptance*.
